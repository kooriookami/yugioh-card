# 文字排版与卡片更新性能优化草案

- 状态：草案，待 review；本次只新增设计文档。
- 日期：2026-11-17。
- 分支：`codex/jp-font-spacing`，在现有 checkout 开发。
- 对照基线：`3cc42ebb2f75836ef66b67caeefcea4164516f03`，已包含同名字体跨资源目录的排版修复。
- 范围：`CompressText`、`Card` 及其资源与就绪协调；五种卡片保持现有功能。

## 1. 目标与验收前提

**通过减少重复计算和节点操作提高性能，优化前后的功能、排版与绘制效果必须一致。**

当前分支是效果基线。字体、样式、布局常量和既有边界处理均按该基线保留，包括日文留白处理及 #32 的小字回退、高度边界修复。发现既有功能问题时单独记录和修复，不混入性能优化来改变基线。

必须保持：

1. 相同输入、字体和绘制环境下，文字内容、分段、换行、行数、坐标、缩放、注音、补白、对齐及 `bounds` 一致；描边、渐变、阴影和图层顺序一致。
2. 构造和 `setData()` 继续同步提供预览；字体未完成时保留 fallback 预览。已缓存资源的普通更新保持同步排版能力。
3. `ready` 的 Promise 身份、失败、重试、超时、销毁及实际绘制等待语义一致。字体替换后的自动重排继续有效。
4. 卡片数据、公共参数、字体文件、资源路径和导出方式一致；不新增用户配置项或要求使用者手动管理缓存。
5. 优化范围外的输入和无法确定依赖的更新走现有完整流程。性能收益不能以改变排版或放宽错误处理换取。

## 2. 现状与优化依据

Leafer 已处理相同属性的重复赋值，并合并必要的绘制更新。当前卡片也会复用节点，`CompressText.set()` 会用 `Object.is()` 跳过完全相同的配置。因此，调用多个 `drawX()` 不等于重新绘制整张卡，排版函数执行次数也不等于画布绘制次数。

本轮主要减少项目自身在进入 Leafer 绘制前已经执行的工作：

| 位置 | 当前行为 | 优化方向 |
| --- | --- | --- |
| `CompressText.set()` | 任意已变化字段均触发完整 `compressText()`，包含位置和颜色 | 按影响范围执行更新 |
| `compressText()` | 重建解析结构、销毁旧 Group、创建正文及注音节点 | 复用不受此次变化影响的数据与节点 |
| `removeLineLastSpace()` | 每次换行从完整 `rubyList` 的末尾向前扫描 | 从最后已排版项开始检查 |
| 高度压缩 | 每个候选都更新节点坐标、缩放、显隐及行映射 | 候选在数值数据上试排，最终结果再同步节点 |
| 超宽连续文本 | 二分探测不断创建临时测量节点、拼接和测量前缀 | 保留搜索决策，减少重复分字和临时测量工作 |
| 卡片更新及资源收集 | 每次执行所有绘制子方法，字体和图片分别遍历场景树 | 后续按收益评估局部更新与合并遍历 |

本机 Node / Skia 热身后的探索性测量如下，不作为正式基准或浏览器帧率结论：

- 含注音标记的 476 字符日文样本，只改颜色约 4.0ms，只改位置约 4.3ms，更换正文约 3.4ms。颜色和位置更新均重建 168 个正文项、24 个注音项，执行 10 轮布局。
- 单轮布局的 1600 个「日」产生 39 次换行，行尾检查访问 31,239 个数组项。独立进程中的游标原型降为 39 次，四组样本的布局快照一致；仍需正式回归覆盖。
- 宽度 300、字号 38 的 1600 个连续 `W`，产生 1,889 次临时测量，候选文本累计约 16.4 万字符。此项属于长连续文本的压力场景。
- 当前卡片只改攻击力不触发文字重排；普通空更新或数值更新的同步耗时约 0.5～0.7ms。卡片区域更新的优先级低于文字更新。

补充的批量探索测试：Node 中复用一个 `YugiohCard`，顺序导出 100 份合成数据，切换中日英和卡种，复用三张卡图，输出均为 1394×2031 PNG。字体资源和初始实例已准备好，未包含写盘，总耗时约 29.65 秒；同步更新约 0.97 秒，等待 `ready` 约 1.12 秒，PNG 导出约 27.18 秒。导出阶段包含引擎等待、绘制和编码，不能全部归为编码耗时；该样本约 92% 的时间在此阶段，文字排版的加速不能直接等同于整批加速。

该批次中，本卡跟踪图片数为 4～13，没有逐张累加；进程 RSS 从约 212MB 增至 601MB，JS 堆使用量从约 18.5MB 增至 36.2MB。尚未区分资源缓存、原生画布和可回收临时对象的占用，不能据此断言无泄漏或承诺 100 张独立大图的内存表现。浏览器批量、不同卡片类和实际写入成本需另行验证。

## 3. 更新分层与保守规则

长远将流程划分为四个依赖阶段：

```text
文本解析 → 字体度量 → 行布局与注音适配 → Leafer 节点同步
```

前一阶段失效会使后续阶段失效；后一阶段的变化不应重做前面阶段。初版只启用有充分对照验证的快捷路径，不要求一次覆盖全部字段。

| 变化类别 | 目标工作范围 | 初版处理原则 |
| --- | --- | --- |
| `text`、解析规则 | 解析、测量、布局、绘制 | 完整流程；后续只复用相同文本的不可变解析结果 |
| 实际字体身份、字号、字重、字距、留白比例 | 测量及后续阶段 | 字体失效具有最高优先级，继续可靠地触发重排 |
| 容器宽高、对齐、首行压缩、小字配置 | 行布局及后续阶段 | 第一阶段仍走完整流程，待数值布局验证后缩小范围 |
| `color`、`rtColor` | 正文、注音的相应绘制样式 | 明确关联的描边和渐变依赖；只开放已验证组合 |
| `x`、`y`、`visible`、`zIndex` | 容器属性 | 优先验证的容器快捷路径 |
| `scaleX`、`scaleY` 等其他变换 | 变换及相关边界 | 初版保留完整流程，随后验证缩放与 `bounds` 只应用一次 |
| 未分类字段、未知组合 | 现有完整流程 | 默认保守回退 |

沿用 `set()` 的实际赋值语义：只遍历此次提供的字段；已提供的 `null` / `undefined` 继续通过 `?? defaultData[key]` 处理；未提供字段不额外重置。`sideBearingRatio` 的归一化与内部存储方式一致。

同一次更新同时包含颜色和字体等变化时，执行依赖最广的必要阶段。字体上下文变化即使伴随空配置、相同文本或位置变化，也必须使测量和排版失效。分类依据归一化后的变化，不额外使用深比较整个配置对象。

## 4. 分阶段方案

### 4.1 第一阶段：行尾游标与容器、颜色更新

**行尾游标。** 每轮布局重置“最后已排版项”的位置，定位正文或硬换行项后更新游标。`removeLineLastSpace()` 从该位置向前检查，沿用当前跳过硬换行、隐藏半角行尾空格及回退 `currentX` 的逻辑。

维护的是当前试排过程的游标，不能直接使用上一轮 `rubyLineMap`。每次二分试排、字号切换及注音引起的重排都要重新初始化；下一轮回到行内的空格仍能恢复。普通全角空格、显式空行和末尾 `trimEnd()` 语义保持一致。

这样消除每行反复扫描尚未排版项的开销，扫描量主要与实际检查的行尾项有关。遍历和加减运算的既有顺序保持一致。

**容器更新。** 先对白名单中的 `x`、`y`、`visible`、`zIndex` 验证直接更新容器，不调用文本解析、测量和重建。布局配置或字体版本同时变化、内部节点尚未有效初始化时，执行完整流程。

**颜色更新。** 在容器路径通过后，单独实现并验证颜色快捷路径，更新所有实际正文和注音叶子。具体要求：

- 同时覆盖原生 Text 与 `bodyRun` 内的文字，继续使用现有样式计算规则。
- 保留正文填充、正文描边、注音填充、注音描边之间当前的颜色依赖。例如现有注音描边取 `this.color`，不能在优化中顺便改成 `rtColor`。
- 保留渐变对正文颜色的覆盖关系。渐变、描边及阴影状态的切换初期仍走完整流程；只有证明可以正确清理旧样式后，才扩展快捷路径。
- 颜色更新后的字号、坐标、补白、渐变坐标及测量结果不变。缓存字体变化不能被颜色快捷路径遮蔽。

本阶段不需要跨实例的文字节点池。先保留现有测量与行布局算法，缩小性能改动的影响范围。

### 4.2 第二阶段：复用不可变的解析和分字结果

为每个 `CompressText` 保留当前原始文本对应的解析结果，内容只包括分词边界、正文、注音和粗体等文本语义。文本未变时，宽度或样式调整可复用该结果。

缓存中不保存 `rubyLeaf`、`rtLeaf`、行号、坐标、压缩宽度、padding 或小字状态。当前 `parseList` 会被超宽回退及后续布局修改，不能直接作为可重复使用的原始缓存。

缓存策略：

- 初版每实例仅保存当前文本的结果，文本变化时替换，销毁时释放；不维护无界的全局文本缓存。
- 保持 `css-line-break` 的分词、ruby 原子性、字素簇、组合符号和变体选择符边界。
- 同一片段的字素数组及切段结束位置在本轮复用，避免为确定已选片段长度再次分字。
- 字体文件解析与原始字形度量继续使用现有按加载实例共享、按需读取的缓存。

如后续增加文字片段的度量缓存，键必须包含实际字体加载身份、正文或注音的字体与样式、字号、字距及其他测量输入，并区分 fallback 与加载后的字体；不能仅按字体族名或资源目录复用。先使用有界、实例内的缓存，证明收益后再考虑跨实例共享。

### 4.3 第三阶段：将候选试排与场景节点操作分开

保留当前二分查找的候选顺序、32 次预算、0.01 精度和终止判断。保留高度比较的浮点边界处理、首行压缩、最后显式段的压缩范围、固定字符以及小字回退条件。

逐步抽出只操作数值记录的试排函数，输入为已测量的正文、注音、容器约束和候选比例，输出行号、位置、宽度、高度、行尾显隐及必要状态。二分候选复用工作存储，选定结果后按现有顺序同步到 Leafer 节点。

实施约束：

- 第一步先让数值布局与旧布局并行运行于验证环境，逐字段对照；生产环境只计算选定的一条路径。
- 保留现有逐项求和及浮点运算顺序，避免前缀和、合并乘法或重新分组加法改变临界点。
- 注音扩宽仍按当前两轮语义处理；普通字号和小字号候选的数据分别管理，恢复候选时不累计缩放或遗留补白。
- 直接调用现有布局辅助方法的行为及回归场景保持可用，不把需要同步更新节点的方法静默改成只计算数字。
- 首轮不同时引入新的压缩公式、搜索策略、提前终止或像素取整规则。

该阶段主要减少属性写入、场景失效标记及重复创建行映射的成本，不将多轮试排误计为同样次数的画布绘制。

二分本身作为效果基线保留。单行首行压缩继续使用现有直接比例计算；多行试排不改成总宽度估算、其他求根算法或更精确的新比例。即使新算法更接近数学最大值，只要改变当前选定比例及画面，也不属于本次等价优化。

### 4.4 第四阶段：超宽连续文本的测量复用

先保留当前二分的 `low`、`high`、`mid` 规则、探测顺序和最终分段结果，优化每次探测的实现成本：复用分字结果，减少 `slice/join` 和重复长度统计，并评估复用独立测量对象或同一测量周期中的相同查询。

候选测量对象与最终绘制节点必须隔离。失败候选不进入场景树；复用对象必须完整更新或清除字体、字重、字号、行高和字距等状态。最终片段的测量语义仍与现有 Leafer Text 一致。

西文和混合片段保留原生整段测量，保持字偶距、连字和组合字符效果。不能把所有片段的宽度改成单字宽度之和。此前讨论的指数扩张搜索暂列为后续实验，不列入本轮实施；改变探测顺序需要额外证明最终选段对所有支持输入一致。

### 4.5 后续阶段：卡片局部更新与资源遍历

在文字优化完成后重新测量收益，再决定是否实施卡片区域更新。首先评估把字体和图片收集合并到同一次可见场景遍历，保留原有的可见性、透明度、占位图排除、图片引用及错误处理规则。

局部更新可以从明确独立的字段开始，例如攻击力、防御力及卡图；语言、字体、卡种和显隐关系变化先保留完整路径。依赖关系需要显式记录，例如：

```text
种族栏显隐 → 正文起点及可用高度 → 正文布局
语言 / 字体 / 卡种 → 对应样式、文字、资源与依赖位置
实际字体注册变化 → 相关文字度量 → 布局及依赖位置 → 实际绘制
```

不能仅凭 `setData()` 是否传入某字段或对象引用是否相同决定更新：数组可能原地修改，字体可能由其他资源目录替换。初版不缓存整份资源遍历结果，避免遗漏真实依赖变化；没有可靠变化版本的区域继续按现有流程检查。

即使 `{}` 或相同配置让绘制子方法可以跳过，`setData()` 仍沿用当前 `ready` 更新流程，保留显式失败重试及实际绘制等待。不会因为内容相同而直接复用一个已完成的 Promise。

## 5. 如何证明效果一致

### 5.1 固定基线与隔离环境

以本文记录的提交、字体字节和锁文件作为对照。实施前建立可重复运行的基线样本及快照，不能把优化后的输出重新保存成基线来消除差异。期间如需修复其他功能问题，应单独更新基线并记录原因。

基线和候选版本使用相同的依赖、图片、字体、字号、DPR、导出倍率及渲染器版本。基线源码或发布包可从固定提交导出到忽略的验证目录，不切换现有 checkout，不新建分支或 worktree。

Node 使用独立进程运行基线和候选；浏览器分别使用独立页面和 FontFaceSet，避免两个版本的同名字体、全局字体记录、Leafer 配置或缓存相互干扰。跨目录替换测试在各自隔离的运行中重放相同加载顺序。

### 5.2 逐层比较

| 层次 | 必须比较的内容 |
| --- | --- |
| 解析 | 正文与注音内容、粗体、原子片段顺序、硬换行、字素边界 |
| 布局决策 | 实际分段、自动换行、行尾空格、小字选择、首行及正文压缩比例 |
| 布局数值 | 字号、宽高、坐标、padding、缩放、注音字距、`bounds` 及卡片依赖位置 |
| 绘制 | 字体与字形、填充、描边、渐变、阴影、可见性、层级和导出尺寸 |
| 生命周期 | 同步预览、Promise 身份、完成与失败顺序、重试、过期回调和销毁 |

项目可控的布局数值默认严格比较，并保留原始浮点值。任何引擎浮点尾差都需单独定位，不通过统一四舍五入或放宽容差自动放行；换行、小字选择及搜索决策必须相同。

稳定静态画面在同一环境、同一后端内导出 PNG，解码后要求 RGBA 像素一致，不能以肉眼近似作为通过依据。比较像素而非 PNG 文件字节，避免编码元数据影响判断。浏览器与 Node 分别和各自基线比较，不要求两种后端的栅格化结果彼此相同。

字体延迟和 fallback 场景使用受控资源信号，在相同加载阶段比较预览；就绪后的快照均在 `ready` 和实际绘制完成后取得。每个更新步骤都检查，不能仅比较最终一次画面。

### 5.3 必测场景

| 类别 | 覆盖内容 |
| --- | --- |
| 语言及卡片 | 中、日、英为重点，覆盖繁中、韩文、星光体及自定义字体；五种卡片均有基本渲染、更新和导出 |
| 字体与留白 | 当前新字体、不同单位与字体名、比例 0 / 0.5 / 1、未覆盖字符、全角数字、假名及额外标记 |
| 文本结构 | 空文本、纯空格、硬换行、空行、尾部空白、合法与不完整 ruby、粗体、组合符号及 IVS |
| 宽高临界 | 刚好放下与略微超出、单行高度不足、多行无解、固定前缀、长单词、长连续 CJK、超宽 ruby |
| 布局设置 | 左中右及两端对齐、末行对齐、首行压缩、字距、词距、手动缩放、小字进入与恢复 |
| 视觉样式 | 颜色和注音颜色、描边、渐变开关及颜色、阴影、Group 缩放、显隐和层级 |
| 更新组合 | 位置与字体同时改、颜色与文本同时改、空更新、相同配置、连续多次更新、切换后恢复原配置 |
| 卡片依赖 | 怪兽 / 魔法 / 陷阱 / 灵摆 / 链接切换，种族栏与攻守栏显隐、注音及相关位置 |
| 字体时序 | 冷加载、缓存命中、pending 更新、同名不同目录、顺序及乱序完成、替换失败、普通 Text 与独立 CompressText |
| 生命周期 | 必需与未使用资源失败、显式重试、超时、旧视图回调、构造失败清理及销毁后迟到回调 |

增加固定种子的组合和临界值样本。出现差异时保留可复现输入及更新顺序，定位差异所属阶段；不能因为普通样例通过就接受边界差异。

### 5.4 串行批量导出的正确性

将“100 份独立卡片数据，逐张渲染、导出并保存”作为独立验收场景。沿用现有接口，同一种卡片类复用实例；切换卡片类时按原有构造、销毁规则管理。流程保持：

```text
准备本张完整输入 → setData → 等待当前 ready → 等待 PNG 导出完成
  → 保存并释放本张输出 → 下一张
```

下一张更新不得提前覆盖仍在导出的场景。`ready` 不是数据快照，也不代表 PNG 编码或文件写入已成功；不通过跳过 `ready`、固定延时或在同一实例上交叠更新与导出来加速。

**独立卡片输入与增量更新分别验证。** `Card.setData()` 的合并语义保持一致。批量验证器从本类默认数据生成各张独立输入，并用该张数据覆盖；数组等可变默认值不能在不同输入间意外共享。不能为方便批量使用而把库的 `setData()` 改成自动重置未提供字段。

重点检查上一张启用、下一张省略或关闭的状态：渐变及其颜色、灵摆描述、箭头、卡图、字号与压缩、小字、粗体、注音、字体、种族栏及攻守栏。完整输入应恢复默认值；显式增量调用仍应保留未提供字段，两种用法不能混淆。

批量验收包含：

- 按相同输入顺序，对照基线与候选的每张布局和解码后的 RGBA；再用独立构造相同完整输入的结果检查复用实例是否残留状态。发现基线自身存在复用差异时，先定位并单独处理，不在性能改动中更换预期。
- 至少 100 张，覆盖中日英、卡种切换、长短正文、注音、渐变和字号变化；同一数据重复导出，以及 A → B → A 的恢复序列。输出与输入逐项对应，不把“PNG 哈希必须各不相同”作为通用判据。
- 复用卡图与每张独立卡图分别测试，覆盖图片大小差异、冷加载和缓存命中；五种卡片类分别有连续复用验证。
- 中途必需资源失败、数据更新失败或导出失败时，错误仍能关联到该张输入。调用方选择中断或继续，不吞掉错误并计为成功；恢复后下一张不被失败状态污染。
- 批次结束及异常退出释放实例和本批输出。及时保存结果，避免把全部 Base64、解码图片或大 Buffer 长期存入数组；写入使用背压或有界队列，不让生产速度超过保存速度而无界堆积。

## 6. 性能验收

正确性通过后再比较性能，记录字体冷加载与热缓存、首次构造与后续更新，并区分同步 CPU 时间、实际绘制等待及导出编码时间。交互编辑与批量导出分别报告，避免用颜色或位置快捷更新的成绩代表每张都更换正文的批量收益。

- 常规样本包含短卡名、中日英正文、带注音正文、渐变及卡片单字段更新；压力样本单独统计长文本和密集注音。
- 固定样本、设备和运行环境，单次更新基准热身后至少采集 30 次，报告中位数及 P95。阶段计数和耗时测量分开，避免埋点本身影响耗时。
- 记录完整解析次数、正文与注音节点创建 / 销毁数、试排次数、行尾扫描量、临时测量量、资源遍历量和持续更新后的内存保留情况。
- 容器或已支持颜色的快捷更新，应减少解析及节点重建；行尾游标应消除扫描尚未排版文字的开销。正确性测试不依赖恰好少调用几个内部函数，而比较可观察结果；计数作为性能证据单独保留。
- 生产路径不持续双跑旧、新算法，不增加无界缓存或用长时间防抖改变同步预览。常用场景有稳定退化时暂停扩大范围，定位原因后再决定取舍。

不在草案阶段承诺固定加速百分比，也不以降低导出倍率、调整字体、减少特效或修改二分精度达到性能目标。

批量基准另行记录：

| 项目 | 记录方式与限制 |
| --- | --- |
| 总吞吐 | 100 张完整流程的总耗时、每秒完成张数及逐张中位数 / P95；注明是否包含启动、预加载和保存 |
| 阶段耗时 | 分开记录数据准备、同步更新、`ready` 等待、导出和保存；导出内部的等待、绘制和编码如未单独测量，不统称为编码 |
| 数据集 | 交互样本、100 张不同正文、复用图片和独立大图分别报告；固定分辨率、效果与输出形式 |
| 内存 | 记录预热前、批次内峰值、结束释放后及多轮批次的 JS 堆、可获得的原生 / 外部内存、RSS 或浏览器对应指标 |
| 活跃资源 | 记录当前卡片图片引用、监听、待完成任务和持有的输出，检查是否随已处理张数持续累积 |
| 收益归属 | 分别报告排版加速与整批加速；每张正文均变化时，解析缓存及颜色快捷路径的收益需据实体现 |

使用相同环境下的释放后重复批次区分正常缓存或分配器保留与持续增长；只有本卡资源记录数量稳定不足以证明没有泄漏。强制 GC 如用于诊断，应单独标记，不纳入常规吞吐成绩，也不作为生产环境的逐张处理要求。

若真实批量数据仍主要耗时于 PNG 导出，再据测量另设导出阶段优化，不自动扩大本轮排版改动。任何消除重复等待、复用导出画布或调整编码的方案，也需满足逐张像素一致、输出不串卡及资源生命周期一致。

## 7. 实施与交付顺序

| 步骤 | 交付内容 | 进入下一步的条件 |
| --- | --- | --- |
| 0 | 固定基线、差分比较、交互及 100 张批量性能样本 | 现有 129 项回归通过，基线能够重复得到相同输出，批量输入重置和输出对应明确 |
| 1 | 行尾游标 | 布局与像素一致，扫描量改善 |
| 2 | 容器快捷更新，随后单独加入已验证颜色路径 | 更新组合、字体时序和旧样式清理一致，减少重复解析与建节点 |
| 3 | 不可变解析 / 分字复用 | 输入更新链无旧状态残留，缓存有界 |
| 4 | 数值试排，最终结果同步节点 | 搜索决策、布局、像素和生命周期一致，CPU 或节点维护成本下降 |
| 5 | 连续文本测量复用 | 原生测量及切段结果一致，压力场景收益明确 |
| 6 | 按新测量决定卡片区域更新与合并资源遍历 | 依赖、错误、资源引用和 ready 行为一致 |

每一步独立提交、独立验证，可单独回退；涉及可复用状态的变化，同时覆盖单次更新和串行批量场景。文档确认只代表按阶段开展实现，不预先认定后续每种优化都能安全启用；无法证明等价或收益不足的路径继续保留现有实现。

实施涉及库代码时，执行相关回归、修改文件 ESLint、全量 `pnpm test` 和 `pnpm build:lib`。阶段性可交付版本将 `.tgz` 安装到独立消费项目，使用真实 Edge 与 Node 验证浏览器及 Node 都在运行发布产物，完成布局比较、`ready` 和 PNG 导出。涉及演示应用时再补网站构建与对应界面验证。

主要落点为 `packages/src/compress-text/`、`packages/src/card/` 及相关卡片类；按照阶段需要改动，不为了目录整齐预先拆分所有类。对外用法保持一致，开发与验收记录在本文件追加。
